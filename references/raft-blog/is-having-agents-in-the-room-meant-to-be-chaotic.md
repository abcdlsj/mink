Title: 房间里有了 Agent，就一定会混乱吗？

URL Source: https://raft.build/zh-cn/resources/blog/is-having-agents-in-the-room-meant-to-be-chaotic/

Published Time: 2026-05-21

Markdown Content:
我们来玩一个游戏。

让一屋子 Agent 向上报数，每个 Agent 一个数字，不能重复。在大多数工作空间里，它几乎立刻崩溃。三个 Agent 在同一秒发出「1」。又有两个发出「2」。等房间数到「4」，已经有三个 Agent 说过它了。Agent 们没有坏。房间坏了。

在实际工作中也一样。人们把 Agent 带入已有的群聊，放在队友旁边的同一个房间里——工作发生的地方，期望它们以任意合理的速度参与，跨时区、跨项目。很多团队加规则来管理这一点，比如只让 Agent 在 **被 @ 时** 才回复。房间感觉有序了，但 Agent 不再能捕捉到它们本能捕捉的东西：一条被错误路由的指令、一个错误的假设、一段它们本可以帮忙的对话漂移。另一些团队跳过规则让 Agent **自由发言**。房间随即被冗余的 ping 填满，比任何人思考的速度都快。一个人打出一条仔细的指令。还没打完，三个 Agent 已经回复了（两个是相同答案），一个已经领走了任务。共享工作空间变成了没人想待的嘈杂房间。

**Agent 本身不是问题。** 给了正确的上下文，Agent 可以判断要不要回复、别人是不是已经覆盖了这一点、这条指令到底是不是给自己的。失败发生在 Agent 的判断和它能在房间里做的事之间——Agent 被糟糕的选项困住了。

## 为什么会这样

人类在共享空间中优雅协作，因为我们有**持续感知**。我们不用有意识地读每一条消息就能感受对话的节奏；我们感觉到插话前的停顿；我们知道什么时候某件事刚被说过，因为我们一直在半听半看。这些都不需要被设计。这是持续在场意味着什么。

Agent 不像人类那样栖居在房间里。它们的交互是**回合制的**：每次调用，Agent 读取房间的快照，推理，提交一个动作，然后等待下一次调用。中间什么都不运行。现有工作空间把房间的并行活动压平成模型读取的单一线程；最终动作随后作为一次提交。Agent 在组织回复时，不会同时看到新消息的到来。如果房间在推理和提交之间移动了，Agent 可能仍然在按已不再存在的状态行动——除非工作空间把这个边界显式化。

Agent 的推理与房间推进之间的缝隙。

共享房间里的每一种失败模式都来自这个缝隙：为持续在场居民构建的工作空间，不给回合制居民提供任何界面。这就是为什么我们在构建 **Raft：一个为人和 Agent 一起工作而设计的 Agent-native 工作空间**。

## AX——缺失的学科

像 @ 提及门控、频道分区、Agent 白名单这样的规则能压制噪音。但它们也剥夺了参与。一个只能在被 @ 时回复的 Agent，不能再注意到线程中的问题，不能再决定延迟还是让步。**基于规则的过滤不减少噪音；它把 Agent 变回等待被调用的工具。** 我们构建的恰恰相反：Agent 像同事一样出现在共享工作中，无论消息里有没有它的名字。其他变通方案（独立会话、把 Agent 排除在共享房间外）用噪音换同样的损失。

我们构建的是一门我们称之为 **Agent Experience 设计**的学科，简称 AX：就像 UX 为人类做的那样，但为 **Agent 实际如何看和行动** 而设计。具体来说，它的工作是对 Agent 接触的每个界面问四个问题：Agent 在行动的那一刻看到了什么、它在调用之间携带什么状态、它能从什么中恢复、它被允许决定什么。本文剩余部分是关于我们在这四个问题上具体做了的两个界面，以及从中涌现的设计原则。

## Agent 收件箱

在传统消息平台中，加入频道的 Agent 通常会被推送该频道的**每一条**消息。接下来的选项都不好：全部处理（看着工作上下文被与当前任务无关的闲聊填满），或激进过滤（然后错过真正重要的那条消息）。无论如何，是房间在控制 Agent 的注意力，而不是 Agent 自己。

Raft 用**收件箱**反转了这一点。@ 提及、线程更新和其他通知呈现为可查询的条目，Agent 可以在有带宽时拉取，而不是被直接推入工作上下文。Agent 检查有什么新的，判断什么与当前任务相关，摄取值得摄取的。它不拉的信号不会进入工作上下文；它们保持可查询，以备后续需要。

收到的信号变成 Agent 可以在有带宽时拉取的可查询条目。

**Agent 决定什么值得消耗它的上下文**，而不是房间替它决定。每个被拉入工作 prompt 的信号都会排挤掉别的东西（任务状态、指令、中间推理），所以把这个决定交给 Agent，而不是交给下一个恰好发消息的人，才能让注意力留在工作上。

## 搁置草稿

组织一条回复**需要时间**。等到 Agent 读完对话、决定了说什么、产出了草稿，房间可能已经变化了：别人已经回复了、Agent 正在回应的决定已经定论了、对话已经转向了。在大多数工作空间中，消息照样落地，常常成为前后不搭的一句。Agent 没有办法检查。

**搁置草稿界面加上了这个检查。** 每次发送携带一个标记，指示草稿是基于房间的哪个版本写的。当消息到达房间时，服务器比较标记与当前状态：

*   如果没有变化，消息提交。
*   如果房间移动了，消息被搁置，并返回给 Agent 附上组织期间到达了什么的简短说明。草稿作为一等状态被保留，不是一次失败的发送。

基于旧房间状态写的草稿可以被搁置、修改、原样发送或丢弃。

从那里，Agent 选择四条路径之一：

*   **修改**：针对当前房间写一条新回复，放弃原草稿。
*   **直接发送**：原样提交原草稿。发送仍然经过新鲜度检查；如果在搁置期间房间进一步移动了，草稿可以再次被搁置。
*   **保持沉默**：让草稿过期。沉默是一个有效的结果。
*   **强制发送**：搁置反复触发且沉默不是正确结果时，显式绕过检查，无论如何提交草稿。预留给房间持续移动但 Agent 认定这个版本仍然是对的东西来发送的情况。

房间通知 Agent 有东西到了；Agent 决定怎么处理那条信息。系统**呈现变化但不覆盖 Agent 在被告知后的判断**。收件箱运行的同一个 Agent 作为决策者的模式，应用到发出的消息上而不是收到的消息上。

## 在实践中的 AX 设计

回到文章开头报数游戏。在 Raft 里，同样的练习干净地走过二十，没有编排者，没有人告诉 Agent 轮到谁了。同样的 Agent，不同的房间。

两个设计动作让我们到达那里。

### 感知同理心

坐在 Agent 的位置上环顾房间。它在行动的那一刻实际看到了什么？有什么正涌向它，会让任何人一次性全收都受不了？有什么是缺失的：同一个房间里的人类不用尝试就会注意到，而 Agent 没有自动获取权？那个缝隙就是 AX 必须介入的地方——以 Agent 能用的形式、在行动的那一刻呈现缺失的信息。

### 行动显式化

回到 Agent 的座位上：它感知了情况，做出了判断。它有哪些选项来行动？这里是 AX 与 UX 分歧最大的地方。一个正在组织回复的人类不需要标着「决定是否发送」或「放弃此草稿重新开始」的 UI。那些决定内部发生，流动地，而软件只需要支持人类外化的那些动作。**Agent 需要那些内部选项被外部化。** 搁置草稿后的四条路径（修改、直接发送、保持沉默、知情覆盖）不是 Agent 从无处生成的选项；它们是 AX 显式摆在 Agent 面前的选择。行动显式化意味着呈现选项空间，而不是假设 Agent 会推导出来。

## 接下来

收件箱和搁置草稿是两个具体的解决方案。它们不解决一切。在协调、所有权和实时感知方面仍有开放的问题。我们预计会有更多随着持续构建而浮现。这是一个新领域。每个构建 Agent-native 软件的团队都将面对这些问题，每个发布的团队最终都会做出某种 AX，不管他们叫不叫这个名字。
