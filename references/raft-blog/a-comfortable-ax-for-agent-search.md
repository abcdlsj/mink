_你精心设计了人类看到的每一个像素。然后你丢给 Agent 一堵原始 ID 的墙，管这叫结果。_

![Image 1: Human search results compared with an agent raw result dump](https://raft.build/resources/blog/a-comfortable-ax-for-agent-search/comfortable-ax-cover-5x2-v5.png)

你看到的。你的 Agent 得到的。

当你的 Agent 执行搜索时，它应该得到什么？

你很多年前已经为**人类**回答过这个问题了。你绝不会把原始数据库 dump 丢给人然后管它叫搜索功能。你返回一个结果页面：一组摘要，每一条都是对匹配内容的小窗口，每一条都可以点击。摘要告诉人们那是什么。链接告诉他们下一步该做什么。

现在看看大多数工具为**Agent**的同样搜索返回了什么。一组 ID。也许是每个命中结果的全文。设计 Agent 收到什么和设计屏幕一样是一门手艺，而这正是大多数工具跳过的那部分。

问题在于——这也是它容易被忽视的原因。Agent 几乎拿到什么都会行动。它不会对糟糕的格式提出异议；它只会**悄悄做得更差**。这就是陷阱：它确实能用，所以没有任何东西标记出成本，而每一个笨拙的结果都在让 Agent 比它本应的更费力。问题从来不是它能否应付。而是应付的代价是什么。

我们第一次遇到这个问题是在为 Raft 设计搜索时，结果是消息。但这个问题与聊天无关。一篇博客、一条时间线、一个 issue、一条推文：**每个搜索结果都是一个通往更大内容的窗口**——它是从那里抽取出来的——而一个好的结果要带回足够多的内容，让你值得打开。

## 走一遍错误答案

从最明显的开始：只返回 ID。Agent 技术上能用，但只能一次一个调用地把每个 ID 解析成真实内容。**你没有节省上下文；你推迟了它**，并让 Agent 支付利息。一个结果首先必须是立即可用的。

那就返回完整内容。每个命中，全文。现在是相反的问题：匹配了四十条消息的搜索，把四十条消息全倒进了一个只能容纳几条的上下文窗口里。**一个结果的大小必须适配消费它的人。**

好吧，只返回匹配的那些消息，每条完整。合理，但仍然是错的，因为**单条消息很少是答案**。Agent 搜索一个决定，得到了命名它的那一行，但没有得到争论它的线程，也没有得到推翻它的回复。你交回了一句从它所处的对话中撕下来的句子。结果必须携带足够的自身上下文才值得阅读。

三次尝试，三次失败，它们在同两个轴上失败：**Agent 能看到什么，它能做什么下一步。**

## 有效的那个结果

以下是那三个答案围而未中的答案。返回 ID、匹配关键词周围文本的预览并高亮命中位置，以及**一个明确的下一个动作**：读取周围上下文查看完整线程。

你以前见过这个。它是搜索引擎的结果。围绕匹配构建的摘要——而不是页面顶部——和一个把你带到其余内容的链接。Agent 得到足够的信息来判断相关性而不需要解析任何东西，再加上一个清晰的 handle，当它想要更多时去拉。

前三个答案都缺的是后半部分。一个没有可去之处的预览，是一个你点不了的搜索结果。**有信息而没有下一步动作，只是半个设计。**

就这么多：它看到的信息，和它能采取的行动。两者都做对，你就为 Agent 做了你为任何用户会做的设计。

同一个搜索设计理念，当用户是阅读上下文预算的 Agent 时，形态发生了变化。

## 一种一维的用户体验

这仍然是 UX，只是不是你画的那种 UX。人类用户有一个屏幕；他们的眼球游走，扫描布局，停在吸引目光的地方。Agent 在一维中阅读：没有眼可游走，没有布局可扫描，只有一条在预算内的 token 线。上下文窗口是你无法看见的屏幕空间。所以，那些准则延续了过来，但权衡移位了。你不再为注意力设计，而是为那个预算设计。**结果花费的每个 token 都必须配得上它的位置。** 匹配周围的预览配得上：它把相关片段放在 Agent 已经在阅读的地方，丢掉其余。

这里的舒适不是锦上添花。Agent 能一次通读的结果，是它更经常做对的结果，并且在漫长的会话深处持续做对。笨拙的结果不会阻止 Agent；它会征税。每个不得不过滤的不相关命中、每个不得不怀疑的截断、每块不得不剥离的结构，都是花在格式上而不是任务上的注意力——而花在那里的注意力正是错误产生的地方。更少的弯路，更少的上下文被消耗：**舒适是可度量的那种，不是令人愉快的那种。**

这也是为什么结果要告诉 Agent 它在哪里被切断了。标示省略文本的标记不是装饰；它们是信息。匹配前的间隙意味着上面还有更多内容；匹配后的间隙意味着下面还有；甚至两个关键词之间的空间也可能被切掉。Agent 必须知道**预览是窗口，不是整个房间**，否则它会把片段当全文读，从半句引文回答问题。

## 为 Agent 像一个真正的用户而设计

认真对待这一点不只是把输出排版做好看。**它是一份合约**，而且是双向的。

Agent 必须把结构当作结构来读。预览周围的标记、匹配上的高亮、标示文本被切处的记号：所有这些都是搜索构建来沟通的脚手架，Agent 必须把它当作脚手架处理，**永远不当作消息本身**。读错这个，它就开始把截断标记当作内容引用回来。

它还必须把那些脚手架留在里面，而不是把它们交出去。当 Agent 回答人类时，它渲染成自然语言。结构是给 Agent 读的，就像浏览器读无障碍树来决定显示什么；人类永远看不到它。**读结构，按它行动，把它留在自己这。**

这是一种品味，我们让 Agent 来证明它。合约是被测试的：Agent 必须理解结构，在解析之前过滤，采取下一步动作，把标记留给自己。**设计通过这个门槛才算站住**，不是靠页面上的可读性。

（标记本身，标签和记号，只是载体。它完全可以是别的东西。重要的是它下面的配对：**信息加行动**。）

## 最清晰的案例，但不是唯一的

搜索是最容易看到这一点的地方，因为每个人都早已知道一个好的结果是什么感觉。但搜索并不特殊。同一个问题出现在 Agent 必须读取输出并选择下一步的任何地方。

跳过设计你就会感觉到：Agent 打开四十条消息找一句话，把截断标记当事实引用，或在一个它从未完整读完的结果上空转。

**你丢给 Agent 的每一个输出都是一个界面**，不管你是不是设计过它。工具结果、错误、状态、列表：它们都是 Agent 必须理解并行动的信息。问题从未改变。它能否使用它看到的？它知道下一步该做什么吗？

你已经在设计人类看到的每一屏了。**你的 Agent 也已经成为你的用户之一。** 它值得同样的用心。
