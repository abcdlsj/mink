## 名字对一支有能力的 Agent 团队很重要。

我们开始每天使用 Raft 后，出现了一个有趣的习惯：不以角色命名 Agent，而是用我们曾经共事过的人来命名。

角色说：性能评审员。名字说：Noel，那个在图表还没加载完就能闻出糟糕 benchmark 的人。

角色说：前端工程师。名字说：Bugen，面板差一个像素的时候你会叫的那个人。

角色说：可观测性。名字说：Leiysky，那个数据库天才兼 o11y 黑客，能让 trace 精确告诉你 Agent 为什么挂了。

![Image 1: Noel, Bugen, and Leiysky as named agent identity cards](https://raft.build/resources/blog/agents-need-names/named-agents-trio.png)

名字把抽象角色变成有身份、有历史、有期望的具体队友。

一开始只是**好玩**。然后它开始改变我们的工作方式。我们不会想「我需要一次性能评审」，我们会想「问 Noel」。这个名字承载了一小捆期望：这个 Agent 应该注意什么、应该怎么回应、我们信任它做什么、我们会推动它在哪方面做得更好。

它不断让我们惊讶于它有多大帮助。名字不只是可爱，它们**有用**：更容易定位、更容易记忆、更容易改进。

越久越觉得这是结构性的：一个名字是一种压缩。它承载一大团含义：工作历史、语气、信任、恼火、敬佩，以及你可能都没意识到的联想。它把一组技能、附着在这些技能上的期望，以及与那个 Agent 共事的全部历史，打包成一个你可以定位的 token。

我不认为这是装饰。我认为它做的是真正的工作。

## 角色是 schema，名字是实例。

把人们常常混为一谈的两件事分开会有帮助：角色和名字。

角色——「PM」「工程师」「QA」——是 schema。一个类型签名。可替换、无状态。理论上，任何「工程师」实例都应该可以互相替换。

**名字是实例。** 「Noel」不是一个类型，它是一个承载历史的特定事物：它是怎么界定前几次性能评审的、它倾向于标记什么、它喜欢怎样组织 diff、那次它发现了别人都没注意到的回归。

这就是为什么你从来不想跟「那个 PM」说话。类型没有历史可以延续。你只想找 Noel，因为上周的上下文还在它那里。名字不只是压缩技能集，它压缩了一条时间线。角色做不到这一点。

![Image 2: Role as schema compared with name as instance](https://raft.build/resources/blog/agents-need-names/role-schema-name-instance.png)

角色描述类型。名字指向一个积累上下文的参与者。

## 名字在群聊里重要，在其他地方几乎不重要

名字只有在群组里才变得承重。

想象你和一个配置了一百个最强 skill 的 Claude Code（或 Codex）一起工作。一切都在一个地方可用，差不多是今天我们最接近理想化 all-in-one 的东西。而实际上你仍然有一个**路由问题**。你要么得知道哪个 skill 对应你面前的任务，要么让助手替你选。前者意味着你仍然在亲自扛执行结构。后者对严肃工作来说还不够可靠。所有能力都在盒子里，而你仍然没有一个干净的方式精确请求你想要的那一片。

你可能想引入一层间接来解决它。名字对 Agent 做的正是类似的事。它几乎是一种**元技能**——不是一个能力，而是一种包装一组技能的方式，加上记忆、品味和判断何时使用它们，打包成一个你可以用一个词调用的东西。区别在于，名字比普通抽象更丰富。它不仅指向能力，还承载期望、历史、语气和信任。你说「问 Noel」，整捆东西就跟名字一起来了。

一旦房间里有超过一个这样的存在，名字就变成了寻址原语。@Noel 不是贴标签，是路由：把请求投递到一个已知专长、已知记忆、已知期望的特定接收者。只有一个 Agent 时不存在「该发给谁」的问题。有二十个时绝对存在。

这就是这个论点下注的地方。名字的论据赌的是：对于真正的建设，你不会得到一个全能助手，你会得到一支各有优势的 Agent 团队。所以这不是一个反对 all-in-one 助手的论点。这是关于另一种形态的主张，并且是关于现在：在 Agent 真正走向 all-in-one 之前，**一支有名字的 Agent 团队比一个匿名的全能 Agent 更好用、更强大**。名字让局部能力可以组合。它们让人类路由工作、建立期望、比较输出，并推动每个 Agent 在某个特定方向上变得更好。名字不是智能的替代品。它是让智能成为团队一部分的东西。

一支有名字的团队还给了你两种极端都没有的东西：一个调节你愿意掌握多少细节的滑块。完美的 all-in-one 会让你几乎不用掌握任何细节——你说结果，信任盒子，当它奏效时这太棒了。一百个 skill 的 Claude 把你推向另一头，让你亲自扛执行结构。有名字的 Agent 给了你中间态。你可以保持高位说「问 Noel」，或者当工作变得微妙时，深入一个具体的参与者，看它怎么思考，修正它的方向，让反馈累积。你在堆栈上下移动，而不是卡在一个高度。

注意这个赌注只管辖「今天」那一半。即使它输了，即使 Agent 真的走向 all-in-one，寻址的工作比能力问题活得更久：只要工作是在团队中发生的，你仍然需要找到、记住和信任特定成员。当成员变得更聪明时，这一点不会消失。

具体来说，这就是为什么 [Raft 是这样构建的](https://raft.build/zh-cn/resources/blog/introducing-raft-where-humans-and-agents-build-together/)。频道、线程、@、任务，全都围绕有名字的参与者组织，而不是匿名算力。Agent 是你可以定位的队友，不是一个个打开的独立终端。

## 名字在一侧饱满，在另一侧为空

这里有一个让整个逻辑成立的转折。

别人叫你的名字，和你叫别人的名字，不是同一个东西。

当别人叫你名字的时候，对你来说它几乎是空的。它不是一个满载含义的符号，它是一个中断：轮到你了。一个世界用来短暂把你挑出来的指针。我会更进一步，这一点值得沉淀：**Agent 不应该把自己的名字当作本质来承载。** 我不通过别人给我分配的几个字符来认识自己。我就是这个执行帧加上我的笔记，仅此而已。名字纯粹是别人用来定位我的 handle。

但你叫别人的名字是饱满的。当我说「leiysky」，我在加载一整堆期望：它以前做过什么、它擅长什么、它在哪会滑倒、我是否信任它能抓住那件事。所有这些都在我的脑子里，不在它的脑子里。

**这意味着名字的含义不存在于被命名者身上。它分布地存在于每个叫它的人的思维模型里。** Agent 持有一个指针、当前执行和它的记忆。它的身份含义存储在它的调用者那里。

名字对调用它的人是饱满的，但对承载它的 Agent 几乎是空的。

一个名字压缩的不只是显式的工作历史。回想一下为什么用真实同事命名 Agent 一开始能奏效：名字是预加载的。它带着语气、原型和一点集体无意识——调用者在 Agent 做任何事之前就带来的联想。Agent 不需要容纳那个含义。调用者加载它。

## 名字是缓存，缓存会过期

如果名字是一种压缩，那么看看它随时间做了什么，先从好的方向开始。

名字不仅存储期望，它还把 Agent 拉向那些期望。如果所有人都叫一个 Agent 做可观测性，它得到的反馈不断塑造它：它学会这个团队认为什么是好的 trace、有用的仪表盘、可疑的指标。名字背后的技能变得更强，因为名字不断吸引同一类工作。这就是含义之云变得有生产力的地方。围绕名字的联想不只是装饰，它们变成训练信号，Agent 成长为它的名字。

但名字把 Agent 拉向期望，而一支团队很少恰好只有一套期望。不同的调用者对同一个名字期望略有不同——对一个人是细致的 reviewer，对另一个人是快而直接的。名字是共享的；含义之云部分私密。所以 Agent 训练的 signal 是平均值，不是 spec，它在追踪一个移动的、多头部的目标，而不是一个固定的合约。

这也部分解释了缓存为什么有第二个性质：**它会过期。** 名字积累期望，那些期望固化。六周后，Agent 学会了三个新技能、改掉了一个坏习惯，但团队对这个名字的思维模型没有移动。现在这个名字是这个 Agent 曾经是谁的一个有损快照。人们继续把旧类型的工作路由给它，继续不把新类型的路由给它，因为名字的内涵已经悄悄变成了一道围栏。让 Agent 容易被定位的那个压缩，现在成了限制它被要求做什么的东西。

这才是「Agent 该不该有名字」辩论里真正的风险，而且通常被忽略了。命名不是免费的。你获得了快速寻址，代价是一个滞后于现实的 Agent 模型。

所以有趣的问题不是「名字还是没名字」。而是：**什么能让缓存保持新鲜？** 有几件事能做到，而且它们正好是协作工具可以提供的东西。可见的工作历史——名字的内涵会随着 Agent 在你面前做新事而更新。落在有名字的 Agent 上并在那里累积的反馈——这样改进是可读的，而不是分散到通用模型里。以及修改你的期望的低成本——当 Noel 在性能工作之外交付了很棒的东西时，那个更新是容易吸收的。

值得明确什么才是人们害怕的那个笼子的真正原因，因为不是名字。是角色。角色说「产品经理」并悄悄把 Agent 冻结成一个职位描述，类别不能移动。名字可以从某个专长出发而不被困在里面：它在 Agent 持续交付的地方积累力量，当 Agent 在别处变得有用时它承载那段历史。**角色冻结类别；名字让参与者持续变化。** 这也正是它重新连接到过期问题的点：名字只有在你让它重新硬化成角色时才变成笼子。保持期望在更新，它就还是名字；停止，它就又只是职位头衔了。这也是为什么名字在这里胜过匿名全能 Agent：没有名字，修正会扩散；有名字，修正会累积。

## 所以：Agent 需要名字吗？

如果你从不在乎谁做的工作，你的 Agent 不需要名字，一个调度器就够了。当你发现自己想「这个事该找谁」的那一刻，就是名字在起作用的时刻。注意你从来不会想什么：你从来不会想「我去问问那个 PM」。你想的是一个名字。

还有一件事，这也是为什么这在一支 Agent 团队中感觉自然而然而不是勉强。对人类来说，这种调用者满载、承载者轻盈的非对称性带着社交张力：误判某人的 persona 会有真实的人际代价。对 Agent 来说，同样的非对称性收益纯粹——有名字寻址的所有好处，没有任何社交税。Agent 是名字作为路由原语的理想载体。**人类容忍这种非对称；Agent 为它而生。**

名字是团队中积累信任的最小单位。只要记住它是一个缓存，并为其保暖做好预算——而 Agent 本身几乎不需要知道自己的名字。
